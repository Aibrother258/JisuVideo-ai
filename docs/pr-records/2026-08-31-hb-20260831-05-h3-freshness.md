## PR 描述（可直接粘贴）

### 背景

对 HB-20260831-01 ~ 04 的外部复盘确认项目已「可运行、可继续开发」，但存在一条 P0 状态同步缺陷与若干 P1 问题。本 PR 按复盘给出的优先级顺序逐项修复，不新增功能按钮。

### P0：刚生成的 H3 提示词可能立刻又被标记为「已过期」

误失效链路（复盘定位）：

1. H3 Agent 保存提示词，同时写入 `minimax_h3_source_hash` / `minimax_h3_generated_at`；
2. 前端生成完成后执行 `refresh()`，用新对象替换当前分镜；
3. `selectedSb` 监听器随即对旧分镜回写一份**内容完全相同**的参考素材；
4. 后端 `PUT /storyboards/:id/reference-assets` 收到保存请求就**无条件**清空 H3 元数据。

数据库抽查佐证：分镜 01 有约 4257 字符的 H3 提示词和两张参考图，但哈希与生成时间均为空。

修复采用**双保险**，任何一层独立成立即可阻断误失效：

**后端：内容感知失效**
- 新增 `backend/src/services/h3-source.ts` 作为来源指纹的**唯一计算入口**。H3 保存时用它记录来源，失效判断时用它比对现状——两个调用点共用同一套算法是修复的必要条件，此前路由与 Agent 工具各自拼字符串算哈希，任何一边调整就会立刻误判。
- `PUT /storyboards/:id/reference-assets` 与 `PUT /storyboards/:id` 均改为：写前算一次指纹 → 事务写入 → 写后再算一次 → **指纹真的变了才清空** H3 元数据。前端回写相同内容、或只 PUT `minimax_h3_prompt`，指纹不变即不失效。

**前端：恢复状态不回写**
- `saveShotRefSelection` 增加**内容签名去重**（类型+URL+顺序）：与最近一次成功写入一致时直接跳过。这条防线与 watcher 触发时机无关，是时序安全的兜底。
- `restoreShotRefSelection` 先记录签名、赋值后 `await nextTick()` 再放开 `restoringShotRefSelection` 标志。此前的标志在 deep watcher 实际执行前就被同步复位，形同虚设。

### P1-1：H3 过期检测覆盖不完整

指纹从「4 个文本字段 + 参考素材」扩展为：

| 输入 | 说明 |
|---|---|
| 分镜文本 | `video_prompt` / `description` / `atmosphere` / `duration` |
| 场景绑定 | `scene_id` + 场景设定图版本（`image_url`/`local_path`） |
| 角色绑定 | `character_ids` + 各自设定图版本 |
| 道具绑定 | `prop_ids` + 各自设定图版本 |
| 额外参考 | 类型 / 角色 / URL / **顺序**（顺序决定 H3 的 `<Picture N>` 编号） |

复盘列出的「更换场景、增删人物/道具、重绘设定图、资产最终图片改变」现在都会正确触发过期。

### P1-2：参考素材保存不稳固

- **事务化**：删除 + 重新插入放进 `db.transaction`，中途失败回滚，不再留下空记录或半套记录。
- **分类上限**：图片 ≤9、视频 ≤3、音频 ≤3、总数 ≤15（与任务接口校验一致），超限返回 400。
- **删除级联**：`DELETE /storyboards/:id` 事务级联清理参考素材；Agent `save_storyboards` 的 `replace_existing`（整集重建换 ID）同样清理。
- **asset_id 透传**：前端从资产库选择 / 本地上传时记录 `refAssetOrigins`（URL → asset_id），随保存请求落库，资产来源可追溯。

### P1-3：MySQL 与浏览器缓存优先级歧义

- **空数组即正式为空**：`GET reference-assets` 请求成功返回 `[]` 表示「确实没有参考素材」，**不回退** localStorage——否则用户清空的素材会被旧缓存复活并写回数据库。
- **仅请求抛错才回退缓存**。
- **保存失败必须提示**：`saveReferenceAssets` 失败改为 toast 报错，不再 `.catch(() => {})` 静默吞掉。

### P1-4：`reference_snapshot` 前后端契约

前端早已发送但后端未接收。现在 `POST /tasks` 归一化接收（只保留字符串数组 + 时间戳，丢弃其余前端状态字段），随 `sys_task.params` 落库，与迭代日志描述闭合。
